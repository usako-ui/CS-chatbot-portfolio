# BOTANICA CSチャットボット MVP

自然派スキンケアEC「BOTANICA」（模擬案件）向けの、AI一次対応型カスタマーサポートチャットボット。
FAQを根拠にAIが自動応答し、AIが答えられない問い合わせだけを人間のオペレーターへ引き継ぐ。

> 実務を想定した模擬案件です。要件定義から設計・実装・テスト・デプロイまでを一貫して行っています。

---

## 解決する課題

| 課題 | 現状 | 目標 |
|---|---|---|
| 返信遅延 | 問い合わせフォームのみ・返信に1〜2日 | AIが数秒で一次回答 |
| 対応集中 | オペレーター2名で月500件を全件手対応 | 定型問い合わせの約70%をAIが処理 |
| 時間外未対応 | 18:00〜翌10:00は翌営業日対応 | 時間外もAIが一次対応し翌営業日案内を返す |

---

## 主な機能

**顧客側**

- ECサイト右下に常駐するチャットウィジェット
- FAQを根拠としたAI自動応答（根拠のない事実は生成しない）
- オペレーターへの引き継ぎ通知と、引き継ぎ後も途切れない会話履歴
- 営業時間外・休日の自動案内
- Supabase Realtime によるオペレーター返信の即時反映

**オペレーター管理画面**

- 問い合わせ一覧（ステータス別・未対応件数バッジ・ログイン時の未対応通知）
- 会話詳細と返信（AIとのやり取りを含む全履歴を確認可能）
- 最初に返信した担当者を自動割り当て
- FAQ管理（追加・有効/無効の切り替え）
- 営業設定（営業時間・定休曜日・休日登録・当日の臨時休業フラグ）

## 設計上のポイント

### 匿名サインインによる RLS と Realtime の両立

顧客はログインしないため、当初は「ブラウザ発行の session_id で本人を識別する」設計だった。
しかしこの方式では顧客に JWT が存在せず、RLS（Row Level Security／行レベルセキュリティ）ポリシーが
常に NULL 判定になって機能しない。かといって匿名ロールに読み取りを許可すると、
全顧客の会話が誰にでも読めてしまう。

そこで **Supabase の匿名サインイン**を採用し、顧客にも JWT を発行して `auth.uid()` で識別する構成にした。
これにより RLS が本来の形で機能し、「顧客は自分の会話しか読めない」と
「オペレーターの返信が Realtime で即座に届く」が同時に成立する。

### 読み取りと書き込みで防御層を分ける

```
[顧客ブラウザ]
   |  匿名JWT（Cookie保存）
   +---- 読み取り ----> Supabase Realtime / SELECT  --RLS--> 自分の会話のみ
   |
   +---- 書き込み ----> Server Action --auth.getUser()で検証--> service_role --> DB
                          ブラウザからの直接書き込みは行わない
```

読み取りは RLS が、書き込みは Server Action が守る。
顧客向け RLS ポリシーを SELECT だけに絞れるため、ポリシーの抜けをレビューで発見しやすい。

実装上、次の2点を特に厳守している。

1. **オペレーター判定に `auth.role() = 'authenticated'` を使わない。**
   Supabase の匿名サインインユーザーもロールは `authenticated` になるため、
   これだけで判定すると匿名顧客に全権限が渡る。`is_anonymous` クレームを見る
   `is_operator()` 関数を経由させている。
2. **Server Action は引数のユーザーIDを信用しない。**
   Server Action の引数はクライアントが改ざんできる。Cookie 上の JWT を
   `auth.getUser()` で署名検証して UID を取得し、会話の所有権を毎回突合している。

### フェイルセーフ設計

- 営業時間の判定に失敗したら「営業時間外」として扱う（守れない約束をしないため）
- AI のエラー・タイムアウト・JSONパース失敗はすべてオペレーターへエスカレーション
- 権限判定でクレームが欠落していたら「権限なし」として扱う

## セットアップ

```bash
# 1. 依存パッケージをインストール
npm install

# 2. 環境変数を設定
cp .env.example .env.local
# .env.local を開き、Supabase と Gemini の値を設定する

# 3. Supabase 側の設定
#    Authentication > Providers > Anonymous を有効化する（必須）
#    未設定だと顧客側の匿名サインインが 422 エラーになる

# 4. 開発サーバーを起動
npm run dev
```

環境変数の詳細と、どのキーがなぜ機密なのかは [.env.example](.env.example) に記載。
